# Connector Reference

## Overview

rsync uses a capability-based connector system: each connector declares what it can do,
and the product decides what to offer from those declarations plus the CDC policy below.

The catalogue in this file is **generated from the connector tree** by
[`scripts/generate_connector_reference.py`](../../scripts/generate_connector_reference.py).
Do not hand-edit the table — run `make connector-reference` after adding, removing or
retyping a connector. CI fails if the table and the tree disagree.

## Capabilities

- **Source** — rsync can read data out of this system.
- **Destination** — rsync can write data into this system.
- **CDC** — Change Data Capture: continuous replication of inserts, updates and deletes.

CDC is **not** simply whatever a connector's `supports_cdc` field says. It is Debezium-backed
and is exposed only for databases on an allowlist, gated first by category — see
[CDC prerequisites](#cdc-prerequisites). The table below reports what the product actually
offers, which is what the API serves (`api-gateway/internal/handlers/tools.go:610`).

## CDC prerequisites

CDC requires a registered source provider. Five families have one; every other connector is
batch-only no matter what its metadata declares. Each provider pre-flights the source before
a pipeline starts, and these are the checks it actually runs:

| Source | Provider | Checked before the pipeline starts |
|---|---|---|
| PostgreSQL | `backend-orchestrator/internal/cdc/postgresql.go:524` | `wal_level=logical`, `max_replication_slots >= 1`, `max_wal_senders >= 1`, and the user holding `REPLICATION` |
| MySQL | `backend-orchestrator/internal/cdc/mysql.go:450` | `binlog_format=ROW`, `binlog_row_image=FULL`, and the `REPLICATION CLIENT` + `REPLICATION SLAVE` grants |
| SQL Server | `backend-orchestrator/internal/cdc/sqlserver.go:235` | login is `sysadmin` or `db_owner`, and SQL Server Agent is Running (without it `fn_cdc_get_max_lsn` stays NULL and capture silently never advances) |
| Oracle | `backend-orchestrator/internal/cdc/oracle.go:223` | database in `ARCHIVELOG` mode, minimal supplemental logging enabled, and LogMiner privileges on the `V_$` views |
| MongoDB | `backend-orchestrator/internal/cdc/mongodb.go:87` | nothing — the checks are deferred to Debezium. MongoDB still **must** run as a replica set; a standalone server fails once streaming starts, surfaced as `MONGODB_NOT_REPLICA_SET` (`api-gateway/internal/notifier/catalog.go:161`) |

Two rules that are easy to get wrong:

- **PostgreSQL provisioning order is fixed**: publication first, then `REPLICA IDENTITY FULL`,
  then the replication slot. Debezium's `publication.autocreate.mode` is held at `disabled` so
  it cannot create these itself and reverse the order. Reversing it loses data silently.
- **The CDC allowlist is hand-mirrored in two files.** `debeziumSupportedDatabases` in
  [`tools.go:588`](../../api-gateway/internal/handlers/tools.go) is the list the API
  serves, and it is the only copy present in a self-hosted image.
  The generator keeps a second copy that ships only in the full tree; a test holds the
  two in step.
  A database absent from the list is batch-only even when its category qualifies —
  ClickHouse and Redshift are both `relational_db` and both batch-only for this reason.

## Adding a connector

Connectors not in the catalogue can be generated from an API's documentation — **in the
hosted service only.** Connector *generation* is stripped from self-hosted images, so if
you are running your own stack skip to the
[developer guide](developer-guide.md) and write the connector by hand. Details of what is
and is not in a self-hosted image:
[what you get when you self-host](../deployment/self-host-feature-boundary.md#connector-generation-what-exactly-is-missing).


```bash
curl -X POST http://localhost:5001/api/v1/connectors/generate \
  -H 'Content-Type: application/json' \
  -H "Authorization: $RSYNC_TOKEN" \
  -d '{"api_name": "salesforce"}'
```

This route is authenticated and workspace-scoped
(`api-gateway/cmd/server/main.go:947`); `$RSYNC_TOKEN` is a session token for the workspace
the connector should belong to. The generator itself runs inside llm-service and is not
reachable from the host — its port is deliberately unpublished, so calling it directly is
connection-refused.

The api-gateway route exists in every build, self-hosted included, because there is no
edition gate. Self-hosted it returns an error: the `tool-generator` container runs
`src.lifecycle.main`, which serves `/v1/deploy` but not `/v1/generate`.

See the [connector developer guide](developer-guide.md) for what to do with the result,
including the template-sync rule for hand-curated connectors.
